<objective>
Build the two admin-facing screens this phase's `/admin/clientes` capability (D-06) has been missing until now, plus the one piece of database work this final plan owns: a `SECURITY DEFINER` Postgres function that answers "is this customer's invitation still pending?" without ever touching `SUPABASE_SECRET_KEY` (per 03-RESEARCH.md's Open Question 2 recommendation — keep the secret-key surface confined to 03-03's two invite/resend functions, per Pitfall 3).

`/admin/clientes` (D-06) gives the admin a searchable list of every customer account — active or still-pending — with an "Invitar cliente" form that works with zero pre-existing reservations (D-11), a "Invitación pendiente" badge plus "Reenviar" button for stuck invites (D-10), and the exact duplicate-email message from D-12 when the admin tries to invite an address that already has an account. `/admin/clientes/[id]` (also D-06, and this phase's admin-side answer to RESA-06's "historial de reservas pasadas por cliente") shows that history as two structurally separate blocks — reservas ya vinculadas (with "Desvincular", D-07) above a search for orphaned reservas by nombre/correo/teléfono (D-08) with "Vincular" (D-04/D-05) below — never merged into one list, per 03-RESEARCH.md's Pitfall 4 and 03-UI-SPEC.md's explicit focal-point requirement for this screen.

Every Server Action this plan's UI calls (`invitarClienteAction`, `reenviarInvitacionAction`, `vincularReservaAction`, `desvincularReservaAction`) already exists, tested, in `app/admin/clientes/actions.ts` from 03-03 — this plan puts pages in front of them, wires them via `useActionState`, and adds the one missing read path (the pending-invite badge) via a new, narrowly-scoped SQL function rather than reaching for 03-03's secret-key client.

Per D-20, the SQL migration (Task 1) is the security-adjacent exception to "code goes through `/codex:rescue` by default" — creating a privileged, `SECURITY DEFINER` database function that reads `auth.users` is exactly the class of decision D-20 reserves for Claude directly, even though (unlike 03-03's secret-key exposure) it never touches `SUPABASE_SECRET_KEY` or the app runtime's environment. Tasks 2 and 3 (the two UI screens) are pure Server Component/Server Action composition over already-tested primitives, with no new privileged surface — delegable to Codex per D-20's default. Per D-23, Task 1 is modeled on **Sonnet**, not Opus: this is explicitly NOT the same risk category as 03-01's WR-01 fix or 03-03's secret-key exposure — it is an additive `SECURITY DEFINER` function following the already-established `private.is_admin()` pattern from Phase 1, reversible by a plain `drop function` with zero blast radius on existing data (see the `<reversibility>` tag on Task 1 for the full reasoning per REVERSIBILITY_GATES). Tasks 2 and 3 are modeled on Sonnet (default tier — UI composition over existing tested actions, no new security decision). Per D-21, never read or print `.env.local`/`.env.admin.local` in full in any task of this plan — this plan's migration workflow uses `npm run db:push`/`npm run db:migrations`/`npm run db:types` exclusively, none of which print secret values. Per D-22, before any task is marked done, run the anti-slop lint checks and the `gsd-code-review` skill (or the Code Reviewer agent) over the diff — never `/thermos`.

- **FA-5 — Server Action calling convention.** All four Server Actions this plan's UI calls (`invitarClienteAction`, `reenviarInvitacionAction`, `vincularReservaAction`, `desvincularReservaAction`) were built by 03-03 with a `(...boundArgs, _previo, formData)` shape, which only works correctly through `useActionState` (a bare `<form action={fn.bind(...)}>` would misalign the arguments and silently swallow any `{error: "..."}` returned on failure). Every button component in Tasks 2/3 wraps its action in `useActionState`, even the zero-field ones (reenviar/vincular/desvincular), specifically to surface `estado.error` per 03-UI-SPEC.md's error-copy contract.
