## Flagged Assumptions

- **FA-1 — AUTH-02/RESA-06 edge probe (`unclassified`/`unresolved`) on this plan's privileged surface.** The deterministic probe could not classify these requirements' text as it applies to secret-key scope and invite/link operations specifically. Resolved as explicit `must_haves.truths` (see frontmatter) plus wired tests, not silently dropped: the secret-key confinement truth and the "no cross-customer leak via the new linking write path" truth are both tested, not assumed.
- **FA-2 — RESEARCH.md Assumption A1 (delete+reinvite mailer behavior, LOW confidence).** The automated test in Task 1 confirms the *database* effects of the delete-then-reinvite workaround (old user gone, new user with fresh `invited_at`), but cannot confirm the real Supabase mailer actually delivers a working, clickable invite email — that is outside what an automated test can observe. Because `workflow.human_verify_mode = end-of-phase`, this is embedded as a `<human-check>` inside Task 1's `<verify>` rather than a blocking mid-flight checkpoint (per `checkpoints.md`'s suppression rule) — it will surface in the phase's consolidated UAT.
- **FA-3 — invite `redirectTo` origin.** Built from the request's own `headers()` (host + protocol) inside the Server Action, not a new `NEXT_PUBLIC_SITE_URL` env var — avoids introducing configuration nobody asked for. This requires the Supabase Dashboard's Auth "Redirect URLs" allow-list to include this app's real origin(s) before an actual invite link click-through works end-to-end (RESEARCH.md Open Question 1) — out of this plan's automated reach (no `/cliente/completar-cuenta` page exists yet to click through to; that is 03-04's job), flagged for confirmation at 03-04/UAT time.
- **FA-4 — D-12 duplicate-email detection via `profiles.email`, not GoTrue's error string.** RESEARCH.md's Pitfall 2 corroborates GoTrue's "already registered" error for a *second invite call*, but its exact machine-readable error code for that case is not documented. Checking `profiles.email` directly (already populated by the existing `handle_new_user` trigger) via the admin client before ever calling `inviteUserByEmail` is more robust and testable than parsing an undocumented error string, and is the design this plan implements.
- **FA-5 — Server Action wiring test strategy.** `app/admin/clientes/actions.ts` has no UI to submit real HTTP forms against yet (`/admin/clientes` is 03-05's job) — Next.js Server Actions cannot be invoked over plain HTTP without a rendered page carrying the build-time action id. This plan's automated tests therefore exercise the underlying `lib/clientes/invitar.ts` / `lib/clientes/vincular.ts` functions directly (matching RESEARCH.md's own Validation Architecture, which names these as `db`-type tests, not `e2e`) plus `npx tsc --noEmit` / `npm run build` for the wiring itself. Full end-to-end HTTP coverage of the four Server Actions arrives in 03-05 once a real page exists to submit forms from.
- **FA-6 — D-06 scope boundary.** D-06 places "the linking action" inside `/admin/clientes` — that route/page does not exist until 03-05. This plan builds only the Server Action layer D-06 depends on; the page itself is explicitly out of scope here.
