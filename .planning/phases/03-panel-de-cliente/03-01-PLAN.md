<objective>
Fix WR-01 for good and give customers a real destination: redesign `iniciarSesion` as a three-way role branch (admin→/admin, customer→/cliente, unrecognized→the same generic error as a wrong password), generalize the single shared role-lookup that already lives in `require-admin.ts` so `requireCliente()` composes it instead of duplicating it, extend the proxy's anonymous-redirect to `/cliente`, and wire a minimal `/cliente` page to a real RLS-scoped query so a customer can log in today and see at least one of their own reservations end to end.

Per D-20, both tasks in this plan are the explicit security exception to "code goes through `/codex:rescue` by default" — WR-01 (D-01/D-02) is D-20's own named example of what Claude implements directly, never Codex. Per D-23, both tasks are modeled on Opus — WR-01 is D-23's explicit justifying case ("decisiones de seguridad como WR-01"). Per D-21, any future revision that delegates a slice of this work to Codex must carry the instruction verbatim: never read or print `.env.local` or `.env.admin.local`; verify a variable exists only via `scripts/check-env.sh`. Per D-22, before either task is marked done, run the anti-slop lint checks and the `gsd-code-review` skill (or the Code Reviewer agent) over the diff — never `/thermos`, which only the user can invoke by typing it themselves.

Purpose: this is the phase's tracer — CONTEXT.md D-01 through D-03 make the WR-01 redesign an acceptance criterion of this phase (ROADMAP Phase 3 Success Criterion #4), not a footnote, and every later plan in this phase (03-02..03-05) builds screens and privileged Server Actions on top of the login/guard/query pipeline this plan proves.

Output: a customer with a real account logs in through the same `/login` form the admin uses, lands on `/cliente`, and reads a real row from `public.reservas` — proven over HTTP without JavaScript, with zero regression to the admin's own login/guard behavior.
</objective>

## Flagged Assumptions

- **FA-1 — AUTH-02 edge probe (`unclassified`/`unresolved`).** The deterministic probe could not classify AUTH-02's Spanish requirement text. Resolved here as an explicit truth plus a wired test, not silently dropped: a customer with zero linked reservations must see none of another customer's data when reading through the *new* `listarReservasCliente()` code path — not just the pre-existing `tests/rls/aislamiento-clientes.test.ts` coverage, which predates this query and this plan's login-redirect fix. See the must_haves truth above and Task 2.
- **FA-2 — UI-SPEC scope split.** `03-UI-SPEC.md`'s populated/empty/loading/error states for `/cliente` (D-14 through D-19: dual badges, "Para: [viajero]", Próximas/Historial split, brand empty state, WhatsApp CTA) are explicitly 03-02's responsibility per `03-PLAN-OUTLINE.md`. This plan ships only the minimal populated case (tipo, fecha, pagador) needed to prove the pipeline end to end — a sequencing choice already made at outline time, not a reduction of D-14–D-19.
- **FA-3 — Server Action cookie read-after-write.** `iniciarSesion` calls the shared `getSessionStatus()` immediately after `signInWithPassword()` succeeds, inside the same Server Action invocation. This relies on `lib/supabase/server.ts`'s `createClient()` reading the same mutable, request-scoped `cookies()` store that `signInWithPassword()`'s `setAll` callback just wrote to — standard `@supabase/ssr` Server Action behavior, not a new assumption this plan introduces. Low risk, self-verifying: if wrong, Task 1's first e2e test ("un cliente con credenciales correctas es redirigido directo a /cliente") fails red immediately, and the documented fallback is to read `data.user.id` from the `signInWithPassword()` response directly for the role lookup instead of a second `createClient()` round-trip.
- **FA-4 — requireCliente()'s wrong-role redirect target.** `03-PATTERNS.md` leaves this as "planner's call, not user-decided." This plan sends an already-authenticated admin who requests `/cliente` to `/admin` (a working destination they're entitled to) rather than `/login?motivo=sin-acceso` (which would look like an error for a legitimately authenticated user). Human-checkable at UAT; a one-line change if the owner disagrees.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Navegador anónimo → POST /login | Credenciales sin autenticar cruzan hacia iniciarSesion(), la puerta compartida admin+cliente |
| Navegador con cookie de sesión → GET /cliente | La cookie afirma identidad; requireCliente() (UX) + RLS (el límite real) reverifican rol y propiedad en el servidor en cada request |
| Next.js (Server Action/Component) → Postgres (Supabase) | Cliente anon/authenticated con RLS habilitado — este plan nunca usa la service-role key |
