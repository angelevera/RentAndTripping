<objective>
Build the landing page D-09's invite mechanism has been missing since 03-03: a customer who clicks "Aceptar invitación" in their real email must land on a working page that turns Supabase's email-link token into an actual session and lets them pick their own password — completing the sentence D-09 already locked ("el cliente elige su propia contraseña, el admin nunca la conoce"). Without this plan, 03-03's `invitarCliente()`/`reenviarInvitacion()` send links that go nowhere real.

Two genuinely different pieces live here, and the project's Codex Delegation Policy (`.claude/CLAUDE.md` §"Codex Delegation Policy") treats them differently:

**Task 1 — `app/auth/confirm/route.ts` — non-delegable, implemented directly by Claude.** This is the one place in the entire codebase that turns an external, unauthenticated token into a real authenticated session (`supabase.auth.verifyOtp`). That is exactly "manejo de sesión," the category the project's Codex policy names alongside WR-01 and RLS as never delegable — not because the mechanism is exotic (it is Supabase's own documented, standard pattern for email-link auth in SSR apps, verified against the installed SDK's own types this session: `EmailOtpType` includes `'invite'`, `VerifyTokenHashParams` is exactly `{token_hash, type}`), but because a mistake here (an unvalidated open redirect, or a type mix-up) is a session-establishment bug, the same class of risk WR-01 was. Modeled on Opus per D-23 ("decisiones de seguridad como WR-01").

**Task 2 — the completar-cuenta page/form/action/schema — delegable to Codex per D-20's default (no secrets, acts only on a session already established by Task 1).** Modeled on Sonnet per D-23 (default tier, no new security decision). Standard instruction for whoever executes this via `/codex:rescue` (D-21): never read or print `.env.local` or `.env.admin.local` in full — this task needs no env var at all, so there is nothing to check via `scripts/check-env.sh` either. Per D-22, before Task 2 is marked done, run the anti-slop lint checks and the `gsd-code-review` skill (or the Code Reviewer agent) over the diff — never `/thermos`. Task 1, though Claude-implemented, gets the same D-22 gate before being marked done, matching 03-01's precedent of applying it to every task regardless of delegation.

Purpose: AUTH-02 names this plan's slice specifically — a page that establishes sessions from external tokens is exactly the kind of surface where AUTH-02's "not just hidden in the UI" requirement can be silently violated (an open redirect, or a response that leaks which tokens are real, are both AUTH-02-shaped bugs even though this plan touches no RLS policy directly).

Output: a customer with a real invite completes their own password on the same session the invite link established, lands on a success screen, and can immediately read `/cliente` with that same session — proven end to end without ever sending a real email (Supabase's mailer only delivers to team members in this project, per existing test-suite convention) by using `generateLink()` to mint a real, verifiable token deterministically.
</objective>

## Flagged Assumptions

- **FA-1 — resolves 03-03's FA-3 (invite `redirectTo` click-through).** 03-03 flagged "out of this plan's automated reach... flagged for confirmation at 03-04/UAT time" because `/cliente/completar-cuenta` didn't exist yet when 03-03 was planned. This plan resolves it concretely: the click-through only works end to end once the Dashboard's "Invite user" template is edited to emit a `token_hash`-shaped link (see `user_setup` in this plan's frontmatter) — Supabase's default `{{ .ConfirmationURL }}` template points at GoTrue's own `/verify` endpoint, which this app's `@supabase/ssr` clients (both configured `flowType: "pkce"`, verified in `node_modules/@supabase/ssr/dist/main/createServerClient.js`/`createBrowserClient.js` this session) cannot complete from an admin-generated link — an invited customer's browser never held the PKCE code verifier an admin-initiated invite would need. The `token_hash` + `verifyOtp` path is the documented, correct mechanism for exactly this case (admin-generated email links), confirmed against the installed SDK's own `VerifyTokenHashParams` type and `EmailOtpType` (`'invite'` is a valid member).
- **FA-2 — automated tests cannot exercise the real email/Dashboard template.** Same structural limit 03-03's FA-2 named for the mailer: an automated test cannot click a link inside a real inbox. This plan's tests instead call `admin.auth.admin.generateLink({type:"invite", email, ...})` directly — the same Admin API method Supabase's own docs point to for testing email-link flows, since it creates the real `auth.users` row and returns `properties.hashed_token` without ever sending mail. This proves every piece of code this plan owns; only the Dashboard template edit itself (`user_setup`) is outside automated reach, and is called out as a `<human-check>` in Task 1.
- **FA-3 — password minimum length.** `lib/validation/completar-cuenta.ts` validates a minimum of 6 characters, matching Supabase Auth's documented default `PASSWORD_MIN_LENGTH`. This project's `scripts/configure-auth.mjs` does not configure this setting, so 6 is assumed unless the live project was configured otherwise. If the real minimum is higher, `updateUser` fails server-side and the existing generic "No pudimos guardar tu contraseña. Prueba otra vez." message covers it — low risk, worth a human glance at UAT.
- **FA-4 — this page never calls `requireCliente()`.** `03-01`'s `requireCliente()` redirects a non-customer session to `/admin` or `/login?motivo=sin-acceso` — neither shows this page's required exact copy ("Este enlace ya venció..."). This page instead reads `supabase.auth.getClaims()` directly (existence-of-session check only, no role lookup, so it does not duplicate the WR-03-flagged role query) and treats any authenticated session as eligible to set its own password — deliberate, not an oversight.
- **FA-5 — no server-side redirect on success.** UI-SPEC's copy ("¡Listo! Ya puedes ver tus reservas. (seguido de redirect a /cliente)") is satisfied here as: the Server Action never calls `redirect()` on success (matching this codebase's established "same-page re-render on `useActionState` without JS" pattern, `login-form.tsx`/`admin-login.test.ts`'s `finalBody` helper), so a no-JS submission gets a 200 response showing the success text plus a real link to `/cliente` — functionally a redirect, navigated by the user (or instantly if a future task adds a client-side `router.push`, not needed for correctness here).

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Enlace de correo (no confiable — puede reenviarse, filtrarse, quedar en el historial del navegador) → GET /auth/confirm | Un `token_hash`+`type` cruza como query string; cualquiera con el enlace puede intentar canjearlo — la expiración y el uso único los aplica GoTrue, no este código |
| GET /auth/confirm → redirect a /cliente/completar-cuenta | El parámetro `next` es entrada controlada por quien construye la URL, nunca debe usarse sin sanear como destino de un redirect |
| Sesión ya autenticada (por cualquiera de las dos vías de arriba) → Server Action guardarContrasena | Solo opera sobre la sesión actual de la request; nunca recibe ni acepta un id de usuario desde el cliente |
