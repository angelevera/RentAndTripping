## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → proxy.ts / admin page / Server Actions | Untrusted cookies and form posts |
| internet → Supabase Auth public endpoints | Anyone holding the publishable key can call signUp/signIn |
| developer machine → Supabase Management API | A personal access token with account-wide power |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-09 | Elevation of Privilege | /admin for a logged-in customer | high | mitigate | requireAdmin() reads profiles.role under RLS and redirects non-admins; e2e customer test (Task 1) |
| T-01-10 | Spoofing | public self-sign-up | medium | mitigate | Sign-up disabled via the Management API; signUp-rejected test (Task 2). The invite-only model comes from ARCHITECTURE Pattern 2 |
| T-01-11 | Elevation of Privilege | Server Actions relying on proxy | medium | mitigate | The guard lives in the page and is documented as mandatory for every admin Server Action; the proxy does only session refresh and an optimistic redirect (Task 1) |
| T-01-12 | Information Disclosure | auth cookie is httpOnly:false (a @supabase/ssr requirement) | medium | accept | Library-mandated so the SDK can read the session. Risk is limited to XSS: no raw-HTML rendering exists in the app, and production runs on HTTPS (Vercel TLS). Revisit if user-generated HTML is ever rendered |
| T-01-13 | Denial of Service | admin locked out by session limits or all-devices sign-out | low | mitigate | Local sign-out scope; configure-auth fails if the time-box, inactivity or single-session limits are on (Tasks 1-2) |
