<objective>
Build the Walking Skeleton (see SKELETON.md). A real person types an admin email and password into the real `/login` form, Supabase Auth signs them in, and they land on `/admin`, whose access decision comes from their real `profiles.role` row read under Row Level Security in the hosted Supabase project. Automated verification uses a namespaced test admin; the real operator account (D-03) is created in Plan 01-02.

Purpose: prove the whole architecture end to end in one thin slice before any expansion. The layers are: Next.js 16 scaffold, `@supabase/ssr` cookies, Supabase Auth, Postgres RLS with `private.is_admin()`, and the page guard. This is the phase's tracer (TRACER_MODE). Task 1 is the mandatory package-legitimacy gate, which must precede any install. Task 2 is the Wave 0 tooling that the orchestrator requested as its own task (Nyquist Wave 0). Task 3 is the tracer.

Output: a scaffolded, linked project; the profiles migration pushed to the hosted DB; the working `/login` → `/admin` path; a green e2e test; and the shared test fixtures every later plan reuses.
</objective>

## Flagged Assumptions (surfaced, not silently resolved)

- **FA-1 — Edge probe AUTH-01 (`unclassified` / `unresolved`).** The deterministic edge probe could not classify AUTH-01 and left it unresolved. The planner did **not** auto-resolve it into a truth. Candidate edges the planner covered explicitly elsewhere:
  - wrong password and malformed email (Plan 01-04 Task 2)
  - a logged-in non-admin (Plan 01-02 Task 1)
  - multiple devices and logout on one device (Plan 01-02 Task 1)
  - rate-limited login (Plan 01-04 Task 2, message mapping only)
  - access-token refresh after expiry: only a static check (the proxy calls `getClaims`) plus a next-day human check. There is no automated expiry simulation.
  Needs human review at verify time.
- **FA-2 — Password recovery email will not reach the operator yet.** CONTEXT assumed email recovery works out of the box. In reality Supabase's default mailer refuses non-team addresses and sends at most 2 messages per hour. Until Phase 5 configures custom SMTP (Resend), the project owner resets the admin password from Supabase Dashboard → Authentication → Users. No task changes this. It is recorded so nobody is surprised.
- **FA-3 — Data model sign-off (RESEARCH A2).** The schema created in Plan 01-03 follows ARCHITECTURE Pattern 2: every client is a Supabase account (a `profiles` row with role `customer`) created by the admin. Plan 01-03 Task 1 carries a human-check so the owner confirms this before Phase 2 builds on it.
- **FA-4 — One hosted Supabase project for development and automated tests.** Test data is namespaced (`rt-test-`) and cleaned up (see the prohibition). A separate production project before real customers go live is a Phase 5 go-live consideration and is not planned here.
- **FA-5 — No Vercel deployment in Phase 1.** The skeleton's deployment line is the documented local full-stack run (see SKELETON.md). The first Vercel Pro deploy is recommended for Phase 2.
